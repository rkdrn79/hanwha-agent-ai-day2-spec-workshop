# 업무 요청: IPS WBS 출고·취소 기능 개선

> 이 문서는 현업 담당자가 전달한 **최초 업무 요청**입니다. 완성된 SPEC이나 설계 문서가 아닙니다.
>
> 수강생은 이 내용을 그대로 구현하지 말고, Claude Code와 미결정 사항을 찾아 질문한 뒤 `docs/SPEC.md`로 구체화합니다.

## 1. 요청 배경

재고 담당자는 프로젝트에 필요한 자재를 WBS 기준으로 확인하고 출고합니다. 현재는 재고 확인, 출고 처리, 취소 여부 확인이 분리되어 있어 업무 흐름을 한 번에 파악하기 어렵습니다. 처리 중 실수가 생기면 실제 재고와 출고 기록이 맞지 않을 수 있고, 같은 요청이 반복되어 재고가 두 번 차감될 가능성도 있습니다.

교육용 MVP에서는 외부 SAP 시스템을 직접 연결하지 않고도 다음 업무 흐름을 한 화면에서 확인할 수 있도록 개선하려고 합니다.

```text
WBS 재고 조회 → 출고 요청 → 재고 차감 → 출고 결과 확인
                                      ↓
                              완료 출고 전체 취소
                                      ↓
                                  재고 원복
```

## 2. 주요 사용자

- **재고 담당자**: WBS별 현재 재고를 확인하고 출고 또는 취소를 수행합니다.
- **업무 관리자**: 출고 결과와 취소 여부가 업무 규칙에 맞는지 확인합니다.

이번 MVP에서는 복잡한 권한 체계나 사용자 인증은 다루지 않습니다.

## 3. 원하는 결과

재고 담당자가 한 화면에서 다음 작업을 수행할 수 있으면 좋겠습니다.

- WBS, 자재, 플랜트, 저장위치별 현재 재고를 조회합니다.
- 출고할 재고와 수량을 선택해 출고를 요청합니다.
- 출고가 완료되면 해당 수량만큼 재고가 줄어듭니다.
- 완료된 출고 건은 전체 취소할 수 있습니다.
- 취소가 완료되면 출고 수량만큼 재고가 다시 늘어납니다.
- 같은 출고 요청이 반복 처리되어 재고가 중복 차감되지 않아야 합니다.
- 처리할 수 없는 요청은 이유를 확인할 수 있어야 합니다.

예를 들어 재고가 `100`인 자재를 `12`개 출고하면 `88`이 되고, 그 출고를 전체 취소하면 다시 `100`이 되는 흐름을 확인하고 싶습니다.

## 4. 현재까지 확인된 업무 정보

WBS 유형에 따라 출고와 취소에 사용하는 SAP 이동유형이 다릅니다.

| WBS 유형 | 출고 이동유형 | 취소 이동유형 |
|---|---:|---:|
| 일반 프로젝트 | `221` | `222` |
| 가수주 | `M75` | `M76` |
| 하자보수 | `M77` | `M78` |

실제 시스템은 IPS에서 SAP 함수를 호출하지만, 교육용 MVP는 외부 시스템 없이 로컬 메모리에서 동작하면 됩니다. 화면을 새로 디자인하는 것보다 출고·취소 업무 규칙이 정확히 동작하는 것이 우선입니다.

## 5. 교육용 MVP 범위

이번 실습에서 우선 다룰 범위입니다.

- 제공된 데모 재고를 조회하는 단일 화면
- 한 종류의 재고를 선택한 출고 처리
- 완료된 출고의 전체 취소 처리
- 출고·취소 후 변경된 재고와 처리 결과 확인
- 자동 테스트와 화면을 이용한 정상·오류 흐름 검증

다음 항목은 이번 MVP 범위에서 제외합니다.

- 실제 SAP 연결과 운영 데이터 사용
- 로그인, 사용자별 권한, 결재
- 부분 취소와 다건 일괄 처리
- 데이터베이스 영구 저장
- 운영 배포, 모니터링, 감사 로그

범위가 서로 충돌하거나 추가 기능이 필요해 보이면 임의로 구현하지 말고 먼저 질문합니다.

## 6. 현재 저장소에 제공된 것

- 한 화면으로 구성된 사용자 인터페이스
- API 경로와 요청 데이터의 기본 형태
- 데모 재고 3건
- 메모리 기반 재고·출고 저장소
- 핵심 업무 규칙을 작성할 빈 함수
- 구현 결과를 확인할 자동 테스트

제공 파일은 출발점일 뿐이며, 현재 테스트가 실패하는 것은 정상입니다. 테스트의 기대값을 바꾸기보다 업무 규칙을 문서로 확정하고 구현을 완성해야 합니다.

## 7. 구현 전에 확인이 필요한 사항

아래 항목은 아직 결정되지 않았습니다. Claude Code에는 먼저 파일 수정을 맡기지 말고, 이 문서와 현재 코드를 읽은 뒤 질문 목록을 만들게 합니다.

- 어떤 값의 조합으로 하나의 재고를 구분할 것인가?
- 출고 수량이 `0`, 음수, 재고 초과일 때 어떻게 처리할 것인가?
- 같은 출고 요청인지 판단하는 기준은 무엇인가?
- 실패한 요청이 재고나 출고 기록을 일부라도 바꿔도 되는가?
- 어떤 상태의 출고만 취소할 수 있는가?
- 이미 취소된 출고를 다시 취소하면 어떻게 처리할 것인가?
- 지원하지 않는 WBS 유형은 어떻게 처리할 것인가?
- 동시에 두 요청이 들어오면 어떤 결과를 보장해야 하는가?
- 성공과 실패를 어떤 상태명과 오류 코드로 표현할 것인가?
- 테스트로 판정할 수 있는 완료 조건은 무엇인가?

## 8. 수강생에게 기대하는 다음 행동

1. Claude Code로 이 문서와 저장소 구조를 읽습니다.
2. 요구사항의 모호함과 충돌 가능성을 질문 목록으로 정리합니다.
3. 강사와 합의한 답을 바탕으로 `docs/SPEC.md`를 작성합니다.
4. SPEC 승인 후 Architecture, ADR, RFC를 작성합니다.
5. 승인된 문서를 참조하는 짧은 Project Skill을 만들고 구현·검증을 수행합니다.

이 문서에는 정답을 모두 적지 않습니다. **업무 요청을 검증 가능한 제품 계약으로 바꾸는 과정 자체가 이번 실습의 시작점**입니다.
