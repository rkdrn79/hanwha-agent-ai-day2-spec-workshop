# 120분 스펙 기반 개발 실습: IPS WBS 출고·취소 MVP

한화 Agent AI 실무교육 2일차 Part 1 실습 저장소입니다. 제공된 **구매시스템(IPS) 입출고 기능개선** 자료에서 핵심 업무만 가져와 다음 사이클을 2시간 안에 완주합니다.

```text
모호한 업무 요청 → 결정 질문 → 구현 스펙 → AI 생성 → 테스트 → 원인 수정
```

완성할 제품은 단순 기능 조각이 아니라 아래 사용자 흐름이 끝까지 작동하는 미니 구매시스템입니다.

```text
WBS 재고 조회 → 출고 처리·재고 차감 → 완료 출고 전체 취소·재고 원복
```

> 실습의 핵심은 코드를 빨리 생성하는 것이 아닙니다. AI가 임의로 판단할 업무 규칙을 스펙으로 고정하고, 생성 결과를 숫자와 상태로 검증하는 것입니다.

## 2. 2시간 범위

### 반드시 구현

- 데모 WBS 재고 조회
- 출고 요청 번호와 수량 입력
- WBS별 이동유형 결정
- 정상 출고 시 재고 차감과 `COMPLETED` 이력
- 출고 완료 건 전체 취소와 재고 원복
- 재고 부족, 중복 요청, 중복 취소 차단
- 자동 테스트와 화면 검증

### 이번에는 구현하지 않음

- 실제 SAP/BAPI 연동
- 전자결재와 메일
- 입고와 품질검사
- 자동·수동 재고 동기화
- 인증·권한·데이터베이스
- 부분 출고·부분 취소
- 단가·금액·회계 처리
- 운영 배포

이 제외 범위는 나중에 만들 기능 목록이면서 동시에, 2시간 동안 AI가 넘지 않아야 할 경계입니다.

## 3. 프로젝트 구조

기존 JB 저장소의 단순한 구조를 유지합니다.

```text
JB/
├── README.md
├── docs/
│   ├── 참고 프로젝트 분석.md
│   ├── 실습 시작 요구사항.md
│   ├── IPS MVP 기능명세.md
│   ├── IPS MVP 구현스펙.md
│   ├── 스펙 작성 가이드.md
│   └── 스펙 템플릿.md
├── src/
│   ├── README.md
│   ├── app.py          # API와 화면 제공
│   ├── engine.py       # 순수 업무 규칙
│   ├── service.py      # 출고·취소 유스케이스
│   ├── store.py        # 메모리 재고·이력
│   ├── data.py         # 데모 재고
│   ├── index.html      # 단일 사용자 화면
│   └── requirements.txt
└── tests/
    ├── test_engine.py
    ├── test_service.py
    └── test_api.py
```

## 4. 시작 전 준비

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r src/requirements.txt
```

자동 검증:

```bash
python -m unittest discover -s tests -v
```

화면 실행:

```bash
python src/app.py
```

브라우저에서 `http://127.0.0.1:8000`을 엽니다.

### 실습 브랜치

| 브랜치 | 용도 |
|---|---|
| `student-start` | 화면·데모 데이터·테스트가 제공되고 핵심 업무 규칙은 `TODO`인 시작점 |
| `main` | 문서와 20개 테스트를 모두 통과하는 강사용 완성 예시 |

수강생은 다음 상태에서 시작합니다.

```bash
git switch student-start
```

시작 브랜치의 실패 테스트는 오류가 아니라 이번 실습에서 구현할 완료 조건입니다.

## 5. 120분 진행안

| 시간 | 단계 | 수강생 행동 | 완료 기준 |
|---:|---|---|---|
| 0~10분 | 문제 이해 | 시작 요구사항과 실제 자료 축소 이유 확인 | 사용자 흐름을 한 문장으로 설명 |
| 10~25분 | 결정 질문 | AI에게 질문만 생성시켜 입력·상태·오류 빈칸 찾기 | 최소 8개 결정 질문 |
| 25~40분 | 스펙 작성 | 답을 결정하고 템플릿에 규칙·결정표·AC 작성 | 핵심 AC 6개와 제외 범위 |
| 40~50분 | 스펙 리뷰 | AI로 모호함·충돌·누락 검토 | 테스트 불가능 문장 제거 |
| 50~75분 | AI 생성 | 승인 스펙 기준으로 코드 생성 | 앱 실행, 정상 출고 가능 |
| 75~95분 | 검증 | 자동 테스트와 정상·오류 화면 확인 | 핵심 시나리오 결과 기록 |
| 95~110분 | 수정 | 실패를 스펙 ID에 연결해 원인 수정 | 테스트를 약화하지 않고 회귀 통과 |
| 110~120분 | 정리 | 변경 전후와 배운 규칙 공유 | 스펙→테스트→수정 연결 설명 |

코드 생성은 전체의 약 25분입니다. 나머지 시간은 업무 결정과 검증에 사용합니다.

## 6. Part 1 실습

### 6.1 모호한 요구사항에서 질문 찾기

먼저 [실습 시작 요구사항](docs/%EC%8B%A4%EC%8A%B5%20%EC%8B%9C%EC%9E%91%20%EC%9A%94%EA%B5%AC%EC%82%AC%ED%95%AD.md)만 읽습니다. 바로 코드를 요청하지 않습니다.

```text
docs/실습 시작 요구사항.md를 읽어줘.
아직 스펙이나 코드를 작성하지 말고 구현 전에 결정해야 할 질문만 찾아줘.

사용자 흐름, 입력, 상태, 오류·경계값, 완료 조건으로 분류하고
문서에서 알 수 없는 답은 임의로 결정하지 마.
```

다음 질문이 나오지 않았다면 추가로 요청합니다.

- 재고를 식별하는 키는 무엇인가?
- 중복 출고를 무엇으로 판단하는가?
- 재고보다 많이 요청하면 부분 처리하는가?
- WBS별 이동유형의 정확한 기준은 무엇인가?
- 부분 취소와 중복 취소 정책은 무엇인가?
- 실패할 때 재고와 이력은 어떤 상태를 유지해야 하는가?

### 6.2 업무 결정하기

AI가 질문을 찾을 수는 있지만 업무 정책을 승인할 수는 없습니다. 이번 실습의 결정은 다음과 같습니다.

| 질문 | 결정 |
|---|---|
| 재고 키 | 자재 + 플랜트 + 저장위치 + WBS |
| 중복 키 | 출고 요청 번호 `request_id` |
| 수량 | 1 이상의 정수, 재고 이하 |
| 재고 부족 | 부분 처리 없이 전체 실패 |
| 출고 상태 | 검증 성공 시 즉시 `COMPLETED` |
| 취소 | 완료 건의 원래 수량 전체만 취소 |
| 중복 취소 | 오류, 추가 원복 금지 |
| 실패 | 재고와 이력 모두 변경 금지 |
| 외부 시스템 | 전부 로컬 모의 처리 |

### 6.3 구현 스펙 작성

[스펙 템플릿](docs/%EC%8A%A4%ED%8E%99%20%ED%85%9C%ED%94%8C%EB%A6%BF.md)에 결정 사항을 반영합니다.

```text
결정한 업무 답변을 반영해 docs/스펙 템플릿.md 형식으로 구현 스펙을 작성해줘.

필수 조건:
- 데이터 식별 키와 상태 전이
- WBS 이동유형 결정표
- 성공 규칙과 실패 후 불변 조건
- FR/ER/AC ID
- 숫자가 포함된 Given/When/Then 인수 조건
- 2시간 제외 범위
```

작성 후에는 [완성 예시](docs/IPS%20MVP%20%EA%B5%AC%ED%98%84%EC%8A%A4%ED%8E%99.md)와 비교합니다. 정답 문장을 복사하는 것보다 누락된 **결정 항목**을 확인합니다.

### 6.4 스펙 리뷰

```text
구현 스펙만 리뷰해줘. 아직 코드는 만들지 마.

다음을 표로 작성해줘.
- 모호하거나 충돌하는 문장
- 누락된 오류와 경계값
- 테스트로 성공 여부를 판정할 수 없는 AC
- AI가 임의로 결정해야 하는 빈칸
- 각 문제의 수정 문장
```

다음 표현이 남아 있으면 수정합니다.

- “적절히 처리한다”
- “필요하면 취소한다”
- “오류를 표시한다”
- “재고를 정상적으로 변경한다”

### 6.5 승인 스펙으로 AI 생성

```text
승인된 구현 스펙을 기준으로 현재 저장소에 구현해줘.
기존 폴더 구조와 API·화면·업무 규칙의 역할 분리를 유지해줘.

먼저 구현할 스펙 ID, 수정할 파일, 검증 방법을 요약하고 시작해줘.
스펙에 없는 기능은 추가하지 마.
완료 후 AC별 검증 결과를 보고해줘.
```

생성 결과에서 먼저 확인할 점:

- 화면 코드에 재고 규칙이 섞이지 않았는가?
- 출고 전에 모든 검증이 끝나는가?
- 중복 요청이 재고를 다시 차감하지 않는가?
- 취소가 원래 수량 전체를 정확히 한 번만 원복하는가?

### 6.6 자동·수동 검증

자동 테스트는 구현 설명이 아니라 스펙의 실행 가능한 판정 기준입니다.

```bash
python -m unittest discover -s tests -v
```

수동 검증은 아래 순서로 진행합니다.

1. `IM24-001` 재고 100을 선택합니다.
2. 요청 번호 `GI-001`, 수량 12로 출고합니다.
3. 이동유형 `221`, 남은 재고 88, 상태 `출고 완료`를 확인합니다.
4. 같은 `GI-001`로 다시 출고해 중복 오류를 확인합니다.
5. 첫 출고를 전체 취소합니다.
6. 이동유형 `222`, 재고 100, 상태 `취소 완료`를 확인합니다.
7. 다시 취소할 수 없고 재고가 100을 유지하는지 확인합니다.

### 6.7 실패 원인으로 수정

```text
실패한 테스트를 해당 AC/FR/ER ID에 연결해줘.
테스트를 지우거나 기대값을 구현에 맞추지 말고 근본 원인을 수정해줘.

보고 형식:
1. 실패한 스펙 ID
2. 기대 결과와 실제 결과
3. 근본 원인
4. 수정 파일과 내용
5. 전체 회귀 테스트 결과
```

좋은 수정 보고 예시:

```text
실패: AC-12 중복 취소 후 재고가 112가 됨
원인: 상태 검증보다 재고 원복을 먼저 실행함
수정: FR-09에 따라 COMPLETED 상태 확인 후에만 원복
검증: AC-12와 전체 회귀 테스트 통과
```

## 7. 핵심 통과 기준

2시간 안에 아래 6개가 확인되면 실습을 완주한 것입니다.

- [ ] 재고 100에서 12를 출고하면 88이 됩니다.
- [ ] 재고 100에서 101을 출고하면 재고와 이력이 바뀌지 않습니다.
- [ ] 같은 요청 번호를 두 번 처리해도 한 번만 차감됩니다.
- [ ] 완료 출고를 취소하면 원래 재고 100으로 돌아옵니다.
- [ ] 같은 출고를 두 번 취소해도 두 번 원복되지 않습니다.
- [ ] WBS에 따라 출고·취소 이동유형이 결정표와 일치합니다.

| “완벽하게 만들어줘” 요청 | 완료 기준을 설명할 수 없음 | 숫자·상태·오류로 완료 정의 |

## 9. 최종 체크리스트

- [ ] 2시간 포함·제외 범위를 설명할 수 있습니다.
- [ ] AI가 결정하면 안 되는 업무 정책을 구분했습니다.
- [ ] 구현스펙에 입력, 키, 상태, 결정표, 오류, AC가 있습니다.
- [ ] 실패했을 때 바뀌지 않아야 할 데이터를 명시했습니다.
- [ ] 생성 결과를 스펙 ID와 테스트로 검증했습니다.
- [ ] 테스트를 약화하지 않고 실패 원인을 수정했습니다.
- [ ] 최종 앱에서 재고 조회→출고→취소를 완료했습니다.
