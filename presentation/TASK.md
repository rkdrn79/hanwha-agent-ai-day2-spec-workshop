# TASK — 완성된 IPS WBS solution을 발표자료로

## 목적

프로젝트·업무 리더가 5분 안에 다음을 이해할 수 있는 발표자료를 만듭니다.

- 왜 이 MVP가 필요한가
- 어떤 업무 계약과 상태 모델을 승인했는가
- 실패 시 재고와 이력을 어떻게 보호하는가
- Frontend·Backend를 어떤 경계로 구현했는가
- 무엇을 근거로 완료라고 판정했는가

## 필수 산출물

1. `output/source_map.md`
2. `output/storyboard.md`
3. `output/ips_wbs_solution_brief.pptx`
4. `output/qa_report.md`
5. `output/generator/` 재생성 소스

## 발표자료 제약

- 6~8장, 16:9, 한 슬라이드에 하나의 메시지
- 제목은 결론이 보이는 문장
- `100 → 88 → 100`, `23/23`, `COMPLETED → CANCELED`의 값과 맥락을 원문과 대조
- 모든 완료 주장에 문서 근거와 판정 테스트를 함께 연결
- SAP·로그인·권한·부분 취소·운영 DB는 범위 밖으로 표시
- 효과·절감률·일정 등 저장소에 없는 수치를 추가하지 않음

## 권장 8장 흐름

1. `100 → 88 → 100`으로 결론을 먼저 보여줍니다.
2. 분리된 확인이 중복 차감·이력 불일치를 만든다는 문제를 제시합니다.
3. 조회 → 출고 → 전체 취소와 두 상태를 보여줍니다.
4. 실패 원자성·중복·재고 부족·재취소 규칙을 보여줍니다.
5. WBS 유형별 이동유형 코드 쌍을 보여줍니다.
6. 계약과 파일 소유권으로 Frontend·Backend를 나눈 경계를 보여줍니다.
7. `23/23`과 브라우저 스모크가 완료를 판정했음을 보여줍니다.
8. 다음 변경은 SPEC·tests부터 시작한다는 기준선으로 닫습니다.

## 통과 기준

- [ ] 출고 수량 12와 88·100 재고가 정확합니다.
- [ ] 상태는 `COMPLETED`, `CANCELED` 두 개만 사용합니다.
- [ ] 실패는 재고·이력·request_id를 바꾸지 않는다고 표현합니다.
- [ ] `221/222`, `M75/M76`, `M77/M78`이 정확합니다.
- [ ] `23/23`을 제품 효과가 아닌 검증 결과로 표현합니다.
- [ ] 최소 5개 주장이 SPEC과 tests 양쪽에 연결됩니다.
- [ ] 전 장을 열거나 렌더링해 겹침·잘림·작은 글씨를 확인합니다.
