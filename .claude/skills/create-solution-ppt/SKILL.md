# Project evidence → PowerPoint

프로젝트의 사실을 근거 추적 가능한 발표 이야기로 변환한다. 특정 저장소 구조, 문서명, 장수, 브랜드 색을 가정하지 않는다.

## 함께 사용할 Skill

실제 PowerPoint 생성·렌더링·구조 검증에는 사용 가능한 `pptx` Skill을 읽고 따른다.

## 1. 작업 Brief를 확정한다

다음 우선순위로 작업 조건을 결정한다.

1. 사용자가 현재 요청에서 명시한 조건
2. 사용자가 지정한 Brief
3. 프로젝트의 `presentation/BRIEF.md` 또는 작업 폴더의 `BRIEF.md`
4. 위 정보가 없을 때만 프로젝트 근거를 조사해 안전한 기본값을 제안

Brief에서 다음 항목을 확인하고, 없는 값만 합리적으로 결정한다.

- 프로젝트 루트와 조사 범위
- 발표 목적과 청중
- 발표 시간, 슬라이드 수 또는 허용 범위, 화면비
- 우선 확인할 근거 위치와 제외할 위치
- 템플릿·스타일 레퍼런스·브랜드 사용 권한
- 작업 폴더, 결과 폴더, 결과 파일명, 언어

사용자 요청과 Brief가 충돌하면 사용자 요청을 따른다. 추론한 값은 작업 폴더의 `design_contract.md` 또는 `storyboard.md`에 가정으로 기록한다.

Brief를 새 프로젝트에서 작성해야 하면 [references/brief-template.md](references/brief-template.md)를 복사해 사용한다.

## 2. 프로젝트 근거를 발견한다

고정된 파일명을 전제로 하지 말고 프로젝트에서 실제로 존재하는 근거를 찾는다.

1. 제품·업무 범위와 요구사항 문서
2. 아키텍처·설계·데이터 흐름 문서
3. ADR·RFC·의사결정 기록과 이슈
4. 테스트·빌드·검증 결과
5. 변경 이력·릴리스 기록
6. 설명의 빈틈을 닫는 데 필요한 소스 코드와 설정

Brief에 근거 우선순위가 있으면 그 순서를 적용한다. 존재하지 않는 문서나 검증 결과를 가정하지 않는다. 문서끼리 충돌하면 한쪽을 자동 선택하지 말고 작업 폴더의 `open_questions.md`에 양쪽 위치와 발표 영향만 기록한다.

## 3. 발표 기준선을 만든다

Brief가 지정한 작업 폴더에 다음 중간 산출물을 만든다. 기본값은 `presentation/work/`다.

```text
source_map.md       주장 → 실제 근거 파일·위치
storyboard.md       청중이 따라갈 이야기와 장면 전환
outline.json        슬라이드 제목·핵심 문장·시각 요소·노트
design_contract.md  선택한 색 역할·레이아웃·타이포·가독성 기준
```

장수와 이야기 구조는 Brief의 목적·청중·시간을 따른다. 한 장에는 가능한 한 하나의 결론만 두고, 제목만 읽어도 전체 논리가 이어지게 한다. 프로젝트 설명에 적합한 실제 파일 구조, 상태 흐름, 데이터, 테스트 근거를 우선 사용한다.

스타일 레퍼런스나 템플릿이 지정되면 실제 파일을 확인하고 시각 문법을 `design_contract.md`로 번역한다. 레퍼런스의 문장·로고·고유 데이터를 복사하지 않는다.
[references/design-contract.md](references/design-contract.md)의 항목으로 시각 기준과 검수 방법을 빠짐없이 기록한다.

## 4. 편집 가능한 PPT를 만든다

- 화면비·장수·언어·결과 파일명은 사용자 요청 또는 Brief를 따른다.
- 모든 핵심 숫자·상태·코드·효과 주장을 `source_map.md`와 대조한다.
- 발표자 노트에는 필요한 근거 위치와 다음 장 연결 문장을 남긴다.
- 생성 소스는 작업 폴더에 두고 결과 PPTX와 렌더·QA 파일은 결과 폴더에 둔다.
- 템플릿이 있으면 마스터·여백·폰트·브랜드 제약을 보존한다.
- 계획이나 구성안만 작성하고 종료하지 않는다.

결과 폴더와 이름이 지정되지 않았다면 `presentation/output/`에 설명적인 파일명을 사용한다.

## 5. Self-refinement한다

1. **Fact:** 핵심 주장과 수치를 원본에 표본 대조한다.
2. **Structure:** 청중과 발표 목적에 맞는 논리인지, 제목만 읽어도 이어지는지 본다.
3. **Visual:** 전 장을 렌더링해 겹침·잘림·작은 글씨·어색한 줄바꿈을 찾는다.
4. **Style:** 지정된 레퍼런스 또는 `design_contract.md`와 contact sheet를 비교한다.
5. **Accessibility:** 대비, 최소 글자 크기, 색상만으로 전달되는 의미를 확인한다.
6. **Repeatability:** PPTX를 직접 덧대지 않고 outline 또는 생성 소스를 수정해 다시 만든다.

QA 보고서에는 Fact, Structure, Visual, Style, Accessibility, Repeatability 결과와 남은 위험을 기록한다.

## 완료 조건

- Brief 또는 사용자 요청의 청중·시간·장수·스타일·출력 조건을 충족했다.
- 핵심 주장마다 실제 근거 위치가 있다.
- 편집 가능한 PPTX와 전 장 렌더, contact sheet, QA 보고서가 있다.
- 구조 검증과 시각 검수를 통과했다.
- 충돌하거나 확인할 수 없는 내용이 사실처럼 표현되지 않았다.

## 금지

- 특정 예제 저장소의 경로·장수·파일명을 다른 프로젝트에 강제하지 않는다.
- 원본에 없는 제품 효과·일정·비용·운영 수치를 만들지 않는다.
- 범위 밖 기능이나 계획을 구현 완료로 표현하지 않는다.
- 발표자료에 맞추기 위해 프로젝트의 문서·소스·테스트를 수정하지 않는다.
- 사용자 승인 없이 회사 로고·고객명·비공개 템플릿을 추가하지 않는다.
