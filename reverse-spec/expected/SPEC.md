# RoomFlow 회의실 예약·승인 SPEC

## 1. 문서 상태

- 상태: Draft
- 입력 원본:
  - `reverse-spec/input/roomflow_screen_definition.pptx`
  - `reverse-spec/input/roomflow_function_definition.xlsx`
- 승인 필요 항목: 조회 기간, 취소 제한, 예약 목적 필수 여부, 응답 기준, 취소 알림, 대리 승인

## 2. 배경과 문제

회의실 예약 흐름이 화면설계서와 기능정의서에 나뉘어 있다. 구현 전에 화면 ID, 입력 검증, 버튼 동작, 상태 전이, 오류 결과를 하나의 계약으로 복원해야 한다. 서로 다른 값과 검토중 항목은 확정 규칙으로 선택하지 않는다.

## 3. 목표

- 임직원이 회의실을 조회하고 단건 예약을 요청할 수 있다.
- 승인자가 요청을 승인 또는 반려할 수 있다.
- 신청자가 본인 예약의 상태와 처리 이력을 확인할 수 있다.
- 실패 시 예약 생성·상태 변경·입력값 보존 결과를 검증할 수 있다.

## 4. 범위

### 포함

- 예약 조회, 단건 예약 입력과 임시저장, 예약 요청
- 내 예약 상세와 처리 이력
- 승인함, 승인, 반려
- 상태 전이와 사용자 오류 메시지
- 승인된 예약의 취소 흐름. 단, 허용 시점은 `OPEN-002` 결정 전까지 미확정

### 제외

- 반복 예약
- 출입 QR
- 외부 캘린더 연동

## 5. 사용자와 역할

- 임직원: 예약 조회와 등록
- 신청자: 본인 예약 상세 확인과 취소 요청
- 승인자: 담당 조직의 `REQUESTED` 예약 승인·반려
- 관리자 대리 승인: `OPEN-006` 결정 전까지 확정 범위 아님

## 6. 핵심 업무 흐름

1. 임직원이 기간·건물·상태 조건으로 회의실 예약을 조회한다.
2. 회의실, 일자, 시작·종료 시각, 참석 인원, 제목을 입력한다.
3. 임시저장하면 `DRAFT`, 예약 요청하면 검증 후 `REQUESTED`가 된다.
4. 승인자는 `REQUESTED`를 승인해 `APPROVED`로 만들거나, 사유와 함께 반려해 `REJECTED`로 만든다.
5. 신청자는 본인 예약의 상태와 처리 이력을 확인한다.

## 7. 상태 모델

```text
없음 ──임시저장──> DRAFT ──예약 요청──> REQUESTED
없음 ─────────────예약 요청────────────> REQUESTED
REQUESTED ──승인──> APPROVED
REQUESTED ──반려──> REJECTED
APPROVED ──취소 정책 충족 후 취소──> CANCELED
```

`APPROVED`, `REJECTED`, `CANCELED` 상태의 요청에 승인 또는 반려를 다시 수행하면 상태를 변경하지 않는다.

## 8. 기능 요구사항

### FR-001. 예약 조건 조회

시스템은 유효한 기간과 선택한 건물·예약 상태를 조합해 예약 목록과 건수를 표시해야 한다. 최초 조회 기간은 `OPEN-001` 결정 전까지 확정하지 않는다.

### FR-002. 조회 결과 보호와 상세 이동

시스템은 본인 예약은 전체 정보를 보여주고 타인 예약의 제목은 숨겨야 한다. 사용자가 본인 예약 행을 선택하면 상세 화면으로 이동해야 한다.

### FR-003. 예약 입력 항목

예약 요청에는 회의실, 예약일, 시작 시각, 종료 시각, 참석 인원, 예약 제목이 필요하다. 예약 목적의 필수 여부는 `OPEN-003` 결정 전까지 확정하지 않는다.

### FR-004. 예약 시간 검증

종료 시각은 시작 시각보다 늦어야 하며 시작·종료 시각은 30분 단위여야 한다. 실패하면 예약을 생성하지 않고 입력값을 유지해야 한다.

### FR-005. 회의실 정원 검증

참석 인원은 1명 이상이고 선택한 회의실 정원 이하여야 한다. 실패하면 예약을 생성하지 않고 입력값을 유지해야 한다.

### FR-006. 중복 예약 검증

같은 회의실의 시간이 기존 예약과 겹치면 시스템은 새 예약을 생성하지 않고 사용자가 입력한 값을 유지해야 한다.

### FR-007. 임시저장

사용자가 초안 필수 항목을 입력하고 임시저장하면 시스템은 예약을 `DRAFT`로 저장하고 상세 화면으로 이동해야 한다. 저장 실패 시 입력값을 유지해야 한다.

### FR-008. 예약 요청

사용자가 필수 입력과 모든 검증을 통과해 예약을 요청하면 시스템은 예약을 `REQUESTED`로 저장하고 승인함에 표시해야 한다.

### FR-009. 예약 승인

승인 권한을 가진 사용자가 미처리 `REQUESTED` 예약을 승인하면 시스템은 상태를 `APPROVED`로 바꾸고 처리자와 처리 시각을 기록해야 한다.

### FR-010. 예약 반려

승인자가 `REQUESTED` 예약을 반려하려면 반려 사유를 입력해야 한다. 성공하면 상태를 `REJECTED`로 바꾸고 사유와 처리자를 기록해야 한다.

### FR-011. 완료 요청 재처리 방지

이미 `APPROVED`, `REJECTED`, `CANCELED`인 예약은 다시 승인하거나 반려할 수 없다. 시스템은 기존 상태를 유지하고 이미 처리된 요청임을 알려야 한다.

### FR-012. 본인 예약 상세

신청자는 본인이 만든 예약의 상태와 처리 이력을 볼 수 있어야 한다. 타인의 상세 접근은 거절해야 한다.

### FR-013. 예약 취소 상태 변경

신청자가 확정된 취소 정책을 충족한 `APPROVED` 예약을 취소하면 시스템은 상태를 `CANCELED`로 변경하고 취소 이력을 표시해야 한다. 정책을 충족하지 못하면 `APPROVED`를 유지해야 한다. 시간 기준은 `OPEN-002`에서 결정한다.

### FR-014. 화면 상태와 입력값 보존

시스템은 Loading, Empty, Validation, Error 상태를 구분해 메시지를 표시해야 한다. 검증 오류와 서버 오류가 발생하면 폼 입력값을 유지해야 한다.

## 9. 데이터와 필드

| 필드 | 형식 | 필수 | 핵심 규칙 |
|---|---|---|---|
| 회의실 | Room picker | Y | 활성 회의실만 선택 |
| 예약일 | Date | Y | 과거 일자 선택 불가 |
| 시작 시각 | Time | Y | 30분 단위 |
| 종료 시각 | Time | Y | 시작보다 늦고 30분 단위 |
| 참석 인원 | Number | Y | 1 이상, 회의실 정원 이하 |
| 예약 제목 | Text | Y | 1~60자 |
| 예약 목적 | Textarea | 미결정 | 최대 300자, 필수 여부는 `OPEN-003` |
| 반려 사유 | Textarea | 반려 시 Y | 최대 300자 |

## 10. 오류와 예외

| 조건 | 오류 코드 | 결과 |
|---|---|---|
| 종료 시각이 시작 이하 | `INVALID_TIME` | 예약 미생성, 입력값 유지 |
| 참석 인원이 정원 초과 | `CAPACITY_EXCEEDED` | 예약 미생성, 입력값 유지 |
| 같은 회의실·시간 중복 | `OVERLAPPED_RESERVATION` | 예약 미생성, 입력값 유지 |
| 반려 사유 없음 | `REJECTION_REASON_REQUIRED` | `REQUESTED` 유지 |
| 이미 처리된 요청 | `ALREADY_PROCESSED` | 기존 상태 유지 |
| 타인 상세 접근 | `FORBIDDEN` | 접근 거절 |
| 서버 오류 | 일반 오류 | 화면 입력값 유지 |

## 11. 비기능 요구사항

확정된 비기능 요구사항은 없다. “사용자가 기다리지 않게 빠르게”는 측정 기준이 없어 `OPEN-004`에서 목표와 측정 구간을 결정해야 한다.

## 12. 인수 조건

### AC-001. 정상 예약 요청

- Given: 활성 회의실과 유효한 시간·인원·제목을 입력했고 같은 시간의 예약이 없다.
- When: 사용자가 예약 요청을 실행한다.
- Then: 예약이 `REQUESTED`로 저장되고 승인함에 표시된다.

### AC-002. 잘못된 시간

- Given: 종료 시각이 시작 시각보다 이르거나 같다.
- When: 사용자가 예약 요청을 실행한다.
- Then: `INVALID_TIME`을 표시하고 예약을 만들지 않으며 입력값을 유지한다.

### AC-003. 정원 초과

- Given: 참석 인원이 선택한 회의실 정원을 초과한다.
- When: 사용자가 예약 요청을 실행한다.
- Then: `CAPACITY_EXCEEDED`를 표시하고 예약을 만들지 않으며 입력값을 유지한다.

### AC-004. 같은 회의실·시간 중복

- Given: 선택한 회의실에 겹치는 기존 예약이 있다.
- When: 사용자가 예약 요청을 실행한다.
- Then: `OVERLAPPED_RESERVATION`을 표시하고 새 예약을 만들지 않는다.

### AC-005. 승인 성공

- Given: 승인 권한이 있고 아직 처리되지 않은 `REQUESTED` 예약이 있다.
- When: 승인자가 승인한다.
- Then: 상태가 `APPROVED`가 되고 처리자와 처리 시각이 기록된다.

### AC-006. 반려 사유 누락

- Given: `REQUESTED` 예약의 반려 사유가 비어 있다.
- When: 승인자가 반려를 실행한다.
- Then: `REJECTION_REASON_REQUIRED`를 표시하고 상태를 `REQUESTED`로 유지한다.

### AC-007. 완료 요청 재처리

- Given: 예약이 이미 `APPROVED`, `REJECTED` 또는 `CANCELED`다.
- When: 승인 또는 반려를 다시 실행한다.
- Then: `ALREADY_PROCESSED`를 표시하고 기존 상태를 유지한다.
