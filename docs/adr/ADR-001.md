# ADR-001: 모든 업무 검증을 저장소 변경 전에 service·engine에서 완결한다

- 상태: 승인됨
- 날짜: 2026-08-14
- 관련 문서: `docs/SPEC.md` 5장(오류 후 불변조건), `docs/ARCHITECTURE.md` 2장(Backend 내부 처리 순서)

## 맥락

제공된 `store.py`는 의도적으로 아무것도 검증하지 않는다. `complete_shipment`는 재고 부족·중복 요청을 확인하지 않고 차감하며 음수 재고도 허용하고, `cancel_shipment`는 상태를 확인하지 않고 무조건 재고를 되돌린다. 없는 키 접근은 `KeyError`로 터져 HTTP 500이 된다.

반면 SPEC의 핵심 불변조건은 "모든 실패는 원자적이다 — 재고·이력·요청 번호 등록을 일부라도 남기지 않는다"이며, 인수 테스트(AC-09, AC-10, AC-12)가 이를 직접 검증한다. 트랜잭션·롤백 기능이 없는 메모리 dict 저장소에서 이 불변조건을 지킬 방법을 정해야 한다.

## 결정

**저장소는 무검증 제공 계층으로 유지하고, 업무 검증 전체를 `engine`(순수 규칙) + `service`(순서 조정)에서 저장소 변경 이전에 완결한다.**

- `service`는 "검증 전부 → 저장소 변이 정확히 1회" 순서를 고정한다(ARCHITECTURE 2장의 6단계).
- `store`가 던지는 `LookupError` 계열과 `KeyError` 가능성은 `service`가 사전 조회로 차단하고 `engine.IpsError`로 변환한다. `app.py`의 `_run`은 `IpsError`만 400으로 바꾸므로, 사용자에게 보여줄 모든 실패는 `IpsError`여야 한다.
- 롤백 코드는 작성하지 않는다. 변이가 마지막 1회뿐이므로 롤백할 중간 상태 자체가 없다.

## 검토한 대안

1. **store에 방어 로직 추가**: 검증이 두 계층에 중복되고, 제공(읽기 전용) 파일을 수정해야 하므로 소유권 규칙과 충돌한다. 기각.
2. **변이 후 실패 시 보상(롤백) 처리**: 보상 로직 자체가 실패하면 불변조건이 깨지고, 테스트로 검증하기 어렵다. 기각.
3. **트랜잭션 지원 저장소(SQLite 등) 도입**: MVP 범위(운영 DB 제외)와 제공 코드 계약을 벗어난다. 기각.

## 결과

- 좋은 점: 실패 원자성이 구조적으로 보장되고, `engine`이 순수 함수로 남아 단위 테스트가 쉬우며, 제공 파일을 건드리지 않는다.
- 감수하는 점: `service`의 호출 순서가 계약이 된다. 순서를 바꾸면 테스트는 통과하더라도 불변조건이 깨질 수 있으므로, 구현 Agent는 ARCHITECTURE 2장의 순서를 임의로 재배열할 수 없다.
- 한계: 단일 프로세스·단일 워커 전제(SPEC 가정 5)에서만 성립한다. 동시 요청 직렬화는 이번 MVP 범위 밖이다.
