# AI 생성 전에 쓰는 MVP 구현 스펙 가이드

기능 명세를 AI가 구현하고 사람이 검증할 수 있는 기준으로 바꾸는 방법을 설명합니다. 예시는 사내추첨 MVP를 사용하지만, 같은 절차를 구매 입출고, 재고 동기화, 과제 관리, VOC 조회에도 적용할 수 있습니다.

## 1. 문서별 역할

| 문서 | 답하는 질문 |
|---|---|
| 참고 프로젝트 분석 | 기존 시스템은 어떤 업무와 구성으로 되어 있는가? |
| 기능 명세 | 누가 왜 어떤 기능을 사용하는가? |
| 구현 스펙 | 이번에 무엇을 어떻게 만들고 언제 완료인가? |
| 테스트 결과 | 실제 구현이 스펙대로 동작하는가? |

기능 명세가 있어도 입력 형식, 오류 처리, 경계값, 완료 조건이 없으면 AI가 빈칸을 추정합니다. 구현 스펙은 그 추정을 줄입니다.

## 2. 좋은 MVP의 조건

- 사용자와 해결할 문제가 명확합니다.
- 입력부터 결과까지 하나의 흐름으로 실행됩니다.
- 정상·오류·경계 상황의 기대 결과가 정해져 있습니다.
- 핵심 업무 규칙이 화면과 분리되어 테스트 가능합니다.
- 이번에 하지 않을 범위가 명확합니다.
- 같은 실패를 다시 재현할 수 있습니다.

기능의 수보다 선택한 흐름의 완결성이 중요합니다.

## 3. 스펙 작성 순서

### Step 1. 사용자 행동을 한 문장으로 정의

```text
<사용자>가 <상황>에서 <입력>을 제공하면,
시스템은 <판단·행동>을 수행하고 <결과>를 제공한다.
```

예시:

```text
행사 진행자가 참여자 이름과 당첨자 수를 입력하면,
시스템은 입력을 검증하고 중복 없는 당첨자를 뽑아 결과와 요약을 제공한다.
```

### Step 2. 포함·제외 범위를 동시에 작성

```text
포함
- 이름 직접 입력
- 중복 제거
- 당첨자 수 검증
- 무작위 추첨

제외
- 로그인
- Excel 업로드
- 블록체인 연계
- 데이터베이스 저장
```

제외 범위는 AI가 좋아 보이는 기능을 임의로 추가하지 못하게 하는 경계입니다.

### Step 3. 결정이 필요한 질문 찾기

#### 입력

- 입력 구분자는 줄바꿈인가, 쉼표인가?
- 빈 줄과 앞뒤 공백은 어떻게 처리하는가?
- 동일 이름은 한 사람인가, 여러 응모권인가?
- 영문 대소문자를 구분하는가?
- 최대 참여자 수는 얼마인가?

#### 처리

- 당첨자 수가 0이면 어떻게 하는가?
- 당첨자 수가 참여자보다 많으면 자동 보정하는가, 오류인가?
- 한 번의 추첨에서 같은 사람이 여러 번 당첨될 수 있는가?
- 랜덤 결과를 테스트에서 어떻게 재현하는가?

#### 출력·저장

- 당첨자 외에 어떤 요약 정보가 필요한가?
- 결과와 참여자 이름을 저장하는가?
- 오류 메시지는 어떤 문장으로 표시하는가?

답을 알 수 없는 항목은 추정하지 말고 `결정 필요`로 분리합니다.

### Step 4. 요구사항에 ID 부여

```text
FR-01 시스템은 각 이름의 앞뒤 공백을 제거한다.
FR-02 시스템은 동일한 이름의 첫 번째 항목만 유지한다.
ER-01 유효한 참여자가 없으면 지정된 오류를 반환한다.
NFR-01 동일한 입력과 테스트 시드는 동일한 결과를 반환한다.
```

| 접두사 | 의미 |
|---|---|
| `FR` | 기능 요구사항 |
| `ER` | 오류·예외 요구사항 |
| `NFR` | 성능, 보안, 재현성 등의 비기능 요구사항 |
| `AC` | 인수 조건 |

한 요구사항에는 한 동작만 담습니다. ID는 코드 리뷰, 테스트, 실패 보고서에서 동일하게 사용합니다.

### Step 5. 입출력 계약 작성

| 입력 | 형식 | 필수 | 제한 | 예시 |
|---|---|---:|---|---|
| `participants` | 문자열 | 예 | 한 줄에 이름 1명 | `김한화\n이태양` |
| `winner_count` | 정수 | 예 | 1~고유 참여자 수 | `2` |
| `seed` | 정수 | 아니요 | 테스트에서만 사용 | `42` |

| 출력 | 형식 | 의미 |
|---|---|---|
| `participant_count` | 정수 | 중복 제거 후 참여자 수 |
| `duplicate_count` | 정수 | 제거한 중복 항목 수 |
| `winner_count` | 정수 | 실제 당첨자 수 |
| `winners` | 문자열 배열 | 중복 없는 당첨자 이름 |

화면, API, 테스트에서 같은 이름과 의미를 사용합니다.

### Step 6. 처리 순서 고정

```text
1. 줄 단위 분리
2. 앞뒤 공백 제거
3. 빈 줄 제거
4. 동일 이름 중복 제거
5. 참여자 존재 여부 검증
6. 당첨자 수 하한·상한 검증
7. 중복 없는 무작위 추첨
8. 결과 요약 반환
9. 실행 이력 기록
```

순서가 바뀌면 결과가 달라질 수 있으므로 산문보다 번호 목록이나 결정표로 고정합니다.

### Step 7. 오류 정책 확정

| 상황 | 정책 |
|---|---|
| 유효한 참여자 없음 | 추첨하지 않고 오류 |
| 당첨자 수 0 이하 | 1로 보정하지 않고 오류 |
| 당첨자 수가 참여자보다 많음 | 참여자 수로 줄이지 않고 오류 |
| 내부 처리 실패 | 기술 오류로 구분해 기록 |

오류를 자동 보정하면 업무 실수를 숨길 수 있습니다. 자동 보정이 필요한 경우에도 스펙에서 명시적으로 승인합니다.

### Step 8. 인수 조건 작성

```text
AC-05
Given 고유 참여자가 2명이고
And 당첨자 수가 3명이며
When 추첨을 실행하면
Then 결과를 생성하지 않고
And "당첨자 수는 참여자 수보다 많을 수 없습니다."를 반환한다.
```

좋은 인수 조건은 다음 특성을 가집니다.

- 실제 입력 예시가 있습니다.
- 화면 또는 반환값으로 관찰할 수 있습니다.
- 제3자가 성공과 실패를 판정할 수 있습니다.
- 하나의 주요 행동을 검증합니다.
- 랜덤, 시간처럼 달라지는 요소는 통제 방법이 있습니다.

### Step 9. 스펙과 검증 연결

| 스펙 ID | 자동 테스트 | 수동 검증 |
|---|---|---|
| AC-01 | `test_ac01_trims_and_removes_blank_lines` | 공백 포함 이름 입력 |
| AC-02 | `test_ac02_removes_duplicates` | 같은 이름 두 번 입력 |
| AC-05 | `test_ac05_rejects_too_many_winners` | 2명 중 3명 추첨 |
| AC-07 | `test_ac07_same_seed_reproduces_result` | 자동 테스트 전용 |

자동화하기 어려운 항목도 검증 방법 없이 남기지 않습니다.

## 4. AI와 스펙을 작성하는 순서

### 1차: 결정 질문만 생성

```text
기능 명세에서 구현 스펙을 만들려고 해.
아직 스펙이나 코드를 작성하지 말고 입력, 처리 규칙, 출력, 오류, 제외 범위에서 결정해야 할 질문만 분류해줘.
```

### 2차: 업무 결정 반영

```text
아래 결정 사항을 반영해 구현 스펙 초안을 작성해줘.
모르는 내용은 추정하지 말고 '결정 필요'로 표시해줘.

<업무 담당자의 답변>
```

### 3차: 검증 가능성 리뷰

```text
스펙을 검토하되 코드는 작성하지 마.
모호한 표현, 충돌하는 규칙, 누락된 오류·경계값, 테스트할 수 없는 인수 조건을 찾아 표로 정리해줘.
각 문제의 수정 문장도 제안해줘.
```

### 4차: 승인된 스펙으로 구현

```text
승인된 구현 스펙을 기준으로 구현해줘.
먼저 구현할 스펙 ID, 수정 파일, 검증 방법을 요약해줘.
스펙에 없는 기능은 추가하지 말고, 완료 후 인수 조건별 검증 결과를 보고해줘.
```

## 5. 코드 생성 전 체크리스트

- [ ] 사용자와 사용 상황이 한 문장으로 설명됩니다.
- [ ] MVP 핵심 흐름이 하나로 좁혀져 있습니다.
- [ ] 포함·제외 범위가 있습니다.
- [ ] 입력 형식, 필수 여부, 제한, 예시가 있습니다.
- [ ] 처리 규칙의 순서가 있습니다.
- [ ] 출력 필드와 사용자 표시 내용이 있습니다.
- [ ] 빈 값, 잘못된 값, 경계값 정책이 있습니다.
- [ ] FR, ER, NFR, AC ID가 있습니다.
- [ ] 인수 조건에 구체적 입력과 기대 결과가 있습니다.
- [ ] 각 AC에 자동 또는 수동 검증 방법이 연결되어 있습니다.
- [ ] 미결정 항목이 별도로 표시되어 있습니다.

스펙의 목적은 문서를 길게 만드는 것이 아니라 AI의 임의 해석을 줄이고 검증 기준을 남기는 것입니다.
