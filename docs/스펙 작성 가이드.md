# 2시간 실습용 SDD·구현 스펙 작성 가이드

이 가이드는 모호한 구매 업무 요청을 AI가 구현하고 사람이 검증할 수 있는 스펙으로 바꾸는 절차입니다. 목표는 긴 문서가 아니라 **AI가 임의로 결정할 빈칸과 수정 범위를 줄이는 것**입니다. 전체 문서 관계는 `docs/SDD 문서 체계.md`를 먼저 확인합니다.

## 1. SDD 문서의 역할

| 문서 | 답하는 질문 | 실습에서의 역할 |
|---|---|---|
| 실습 시작 요구사항 | 현업은 무엇을 원한다고 말했는가? | 모호함 찾기 |
| 기능명세 | 누가 어떤 흐름을 어디까지 사용하는가? | 범위 합의 |
| 구현스펙(SPEC) | 최초 목표의 입력·규칙·오류·완료를 어떻게 판정하는가? | 승인된 초기 설계 기준선 |
| ADR | 왜 이 설계 결정을 선택했는가? | 중요한 판단의 이유 보존 |
| RFC | 이번 작업에서 AI가 무엇을 건드려도 되는가? | 수정 허용·금지 범위 강제 |
| 테스트 | SPEC대로 동작하는가? | 실행 가능한 판정 기준 |
| `CHANGELOG.md` | 검증 후 실제로 무엇이 바뀌었는가? | 유지보수 변경이력 |

SPEC은 코드와 함께 계속 갱신하는 운영 일지가 아닙니다. 승인된 최초 설계는 보존하고, 이후 실제 변경은 CHANGELOG에 기록합니다. 중요한 결정이 바뀌면 새 ADR을, 제품 계약이 바뀌면 새 버전의 SPEC을 작성합니다.

## 2. 바로 코드를 생성하면 안 되는 이유

“출고하면 재고를 줄이고 취소하면 돌려놓는다”만 주면 AI는 다음을 임의로 결정합니다.

- 재고 부족 시 가능한 수량만 부분 출고할지
- 같은 요청을 재전송하면 성공으로 볼지 오류로 볼지
- WBS별 이동유형을 어떻게 구분할지
- 일부 품목 취소를 허용할지
- 취소를 두 번 실행하면 재고를 두 번 더할지
- 오류가 나기 전에 변경한 재고를 되돌릴지

이 결정은 코딩 취향이 아니라 업무 정책입니다.

## 3. 20분 안에 초기 SPEC을 만드는 순서

### Step 1. 시작과 완료를 한 문장으로 고정

```text
재고 담당자가 WBS 재고와 수량을 선택해 출고하면 재고가 차감되고,
완료 출고를 전체 취소하면 같은 수량이 원복된다.
```

### Step 2. 포함·제외 범위를 동시에 작성

```text
포함: 재고 조회, 출고, 이동유형, 전체 취소, 오류 검증
제외: 실제 SAP, 결재, 메일, 자동 동기화, 인증, DB
```

제외 범위는 일정표가 아니라 이번 생성에서 AI가 넘지 않아야 하는 경계입니다.

### Step 3. 상태와 데이터 식별 키 결정

```text
재고 키 = 자재 + 플랜트 + 저장위치 + WBS
출고 상태 = COMPLETED → CANCELED
중복 키 = request_id
```

상태마다 허용 행동을 표로 쓰면 조건문과 테스트가 명확해집니다.

### Step 4. 결정표 작성

```text
WBS R2-00* → 출고 M75 / 취소 M76
WBS R2-01* → 출고 M77 / 취소 M78
그 외       → 출고 221 / 취소 222
```

여러 조건에서 결과가 달라지는 규칙은 산문보다 결정표가 안전합니다.

### Step 5. 실패 후 불변 조건 작성

| 실패 | 하지 않아야 할 일 |
|---|---|
| 재고 부족 | 일부 차감, 출고 이력 생성 |
| 중복 요청 | 두 번째 차감, 중복 이력 생성 |
| 중복 취소 | 두 번째 재고 원복 |
| 존재하지 않는 출고 | 임의 데이터 생성 |

정상 결과보다 이 표가 수정 실습에서 더 중요합니다.

### Step 6. 인수 조건을 숫자로 작성

```text
Given 재고가 100이고 출고 수량이 12일 때
When 출고하면
Then 상태는 COMPLETED이고 재고는 88이다.

Given 위 출고가 완료되었을 때
When 전체 취소하면
Then 상태는 CANCELED이고 재고는 100이다.
```

“정상 처리한다” 대신 입력값과 관찰 가능한 결과를 씁니다.

## 4. 요구사항 ID 규칙

| 접두사 | 의미 | 예시 |
|---|---|---|
| `FR` | 기능·업무 규칙 | FR-04 재고 부족이면 전체 실패 |
| `ER` | 오류 계약 | ER-05 중복 요청 오류 |
| `NFR` | 품질·보안·재현성 | NFR-01 규칙 자동 테스트 |
| `AC` | 인수 조건 | AC-11 취소 후 재고 원복 |

한 ID에는 한 가지 판단만 담고 코드, 테스트, 실패 보고서에서 같은 ID를 사용합니다.

## 5. 실습용 AI 프롬프트

### 질문만 만들기

```text
docs/실습 시작 요구사항.md를 읽어줘.
아직 스펙과 코드는 작성하지 말고 결정이 필요한 질문만 분류해줘.
문서로 알 수 없는 답은 추정하지 마.
```

### 구현 스펙 초안 만들기

```text
결정한 답변을 반영해 docs/스펙 템플릿.md 형식으로 구현 스펙을 작성해줘.
모든 규칙에 ID를 부여하고 다음을 반드시 포함해줘.
- 입력 필드와 식별 키
- 상태 전이
- WBS 이동유형 결정표
- 오류 후 불변 조건
- Given/When/Then 인수 조건
- 제외 범위
```

### 스펙 리뷰하기

```text
작성한 스펙을 검토해줘. 코드는 만들지 마.
모호한 표현, 충돌, 누락된 경계값, 테스트할 수 없는 완료 조건을 찾아줘.
각 문제마다 문제가 되는 이유와 수정 문장을 제안해줘.
```

### 승인 스펙으로 구현하기

```text
docs/IPS MVP 구현스펙.md, 관련 ADR, 승인된 RFC를 읽어줘.
RFC의 수정 허용 파일만 변경하고 금지 작업을 하지 마.
먼저 구현할 스펙 ID와 수정 파일을 요약하고 시작해줘.
범위 밖 수정이 필요하면 멈추고 질문해줘.
완료 후 인수 조건별 테스트 결과와 CHANGELOG 후보 문구를 보고해줘.
```

### 실패에서 수정하기

```text
실패한 테스트와 연결된 AC/FR/ER ID를 찾아줘.
테스트를 약화하거나 기대값을 바꾸지 말고 근본 원인을 수정해줘.
승인된 RFC 범위 밖 파일은 수정하지 마.
수정 후 전체 회귀 테스트 결과, 영향받은 스펙 ID, CHANGELOG 후보 문구를 보고해줘.
```

## 6. 코드 생성 전 체크리스트

- [ ] 사용자와 완료 결과가 한 문장으로 설명됩니다.
- [ ] 2시간 포함·제외 범위가 나뉘어 있습니다.
- [ ] 데이터 식별 키와 중복 판단 키가 있습니다.
- [ ] 입력의 필수 여부와 경계값이 있습니다.
- [ ] 상태와 허용 행동이 정해져 있습니다.
- [ ] 조건별 결과는 결정표로 표현했습니다.
- [ ] 모든 오류에 데이터 불변 조건이 있습니다.
- [ ] 인수 조건에 구체적인 숫자와 결과가 있습니다.
- [ ] AC가 자동 또는 수동 검증과 연결되어 있습니다.
- [ ] 미결정 업무 정책을 AI가 임의로 채우지 않았습니다.
- [ ] 중요한 설계 선택의 이유를 ADR에 기록했습니다.
- [ ] RFC에 AI 수정 허용·금지 파일과 중단 조건이 있습니다.
- [ ] SPEC에 변경이력을 쌓지 않고 `CHANGELOG.md`를 별도로 사용합니다.

## 7. 좋은 수정 보고서 형식

```text
실패: AC-12 중복 취소 시 재고가 112로 증가
원인: 취소 전에 CANCELED 상태를 검사하지 않음
수정: FR-09에 따라 상태 검사 후에만 원복하도록 순서 변경
검증: AC-12 및 전체 회귀 테스트 통과
변경이력: CHANGELOG의 Fixed 항목 후보 작성
```

“고쳤습니다”보다 스펙 ID, 원인, 수정, 회귀 결과를 연결해야 다음 작업에서도 재사용할 수 있습니다.
