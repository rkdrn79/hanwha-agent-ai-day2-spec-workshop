# SPEC: IPS WBS 출고·취소 MVP

이 문서는 이 제품의 **최초 계약**입니다. `docs/요청사항/`의 업무 요청과 `tests/`의 인수 테스트를 근거로 범위·용어·상태·불변조건·인수 조건을 고정합니다. 구현 중 발생하는 변경 이력은 이 문서에 덧붙이지 않고 루트 `CHANGELOG.md`에 기록합니다. SPEC 자체를 바꿔야 하는 결정이 생기면 사람 승인 후 개정하고, 개정 사실만 CHANGELOG에 남깁니다.

## 1. 범위

### 포함

- WBS 재고 조회와 WBS 정확 일치 필터
- 재고 행 선택 → 출고 요청(요청 번호·처리자·수량) → 재고 차감
- 완료된 출고 1건의 **전체 취소**와 재고 원복
- 출고 이력 조회(상태·수량·이동유형·취소 정보)
- 실패 이유의 화면 표시, 요청 중 중복 클릭 방지
- 데모 초기화

### 제외 (요청사항 `00-업무-배경.md` 확정)

- 실제 SAP 연동, 로그인·권한·전자결재
- 부분 취소, 다건 일괄 처리
- 운영 DB·배포·모니터링, 단가·금액·메일링

## 2. 용어

| 용어 | 정의 |
|---|---|
| 재고 항목 | `(material_code, plant, storage_location, wbs)` 4개 값의 조합으로 유일하게 식별되는 가용 수량 |
| 출고(Shipment) | 하나의 재고 항목에서 요청 수량을 차감하는 트랜잭션. `shipment_id`(1부터 증가하는 정수)로 식별 |
| 출고 요청 번호(`request_id`) | 담당자가 부여하는 중복 처리 방지용 문자열. 성공한 출고 전체에서 유일해야 함 |
| 전체 취소 | 완료된 출고의 **원 출고 수량 전체**를 재고에 되돌리는 행위. 부분 수량 취소는 없음 |
| 이동유형(movement type) | SAP 자재 이동을 구분하는 코드. 이 MVP에서는 WBS 업무 유형이 결정하는 출고/취소 코드 쌍 |

### 이동유형의 의미

`221/222` 등은 임의의 숫자가 아니라 **WBS의 업무 유형별 출고·취소 코드 쌍**입니다.

| WBS 업무 유형 | 의미 | 출고 코드 | 취소 코드 |
|---|---|---:|---:|
| 일반 프로젝트 | 정식 수주된 프로젝트 WBS에 대한 자재 출고 | `221` | `222` |
| 가수주 | 수주 확정 전 선행 착수(가수주) WBS에 대한 출고 | `M75` | `M76` |
| 하자보수 | 하자보수 WBS에 대한 출고 | `M77` | `M78` |

취소 코드는 항상 같은 행의 출고 코드와 쌍으로 사용합니다. 다른 유형의 코드를 섞어 쓰는 것은 업무 규칙 위반입니다.

## 3. 상태 모델

출고는 두 상태만 가집니다. 상태 문자열은 대문자 원문이 계약입니다.

```text
(생성 없음: 검증 통과 시에만 레코드가 생김)
COMPLETED ──전체 취소──> CANCELED   (종결, 재취소 불가)
```

- `COMPLETED`: 검증을 통과해 재고가 차감된 출고. 취소 가능.
- `CANCELED`: 전체 취소되어 재고가 원복된 출고. 어떤 전이도 불가.
- `PENDING`·부분취소 같은 중간 상태는 존재하지 않습니다. 실패한 요청은 레코드 자체를 만들지 않습니다.

## 4. 업무 불변조건

1. **식별**: 재고는 자재·플랜트·저장위치·WBS 조합으로 찾는다. 조합이 없으면 출고는 실패한다.
2. **수량**: 출고 수량은 1 이상의 정수다. 0과 음수는 거부한다.
3. **재고 하한**: 가용 재고보다 큰 수량은 출고할 수 없다. 재고는 음수가 될 수 없다.
4. **멱등**: 성공한 출고의 `request_id`는 재사용할 수 없다. 같은 번호의 재요청은 거부되고 재고는 한 번만 차감된다.
5. **전체 취소**: 취소는 `COMPLETED` 상태에서만 가능하고, 원 출고 수량 전체를 원복하며, 취소자·취소 시각·취소 이동유형을 기록한다.
6. **재취소 금지**: `CANCELED` 건의 취소 요청은 거부되고 재고는 변하지 않는다.
7. **이동유형 쌍**: 출고 시 WBS 업무 유형의 출고 코드를, 취소 시 같은 유형의 취소 코드를 사용한다.
8. **필수 입력**: 문자열 입력은 앞뒤 공백을 제거하고, 공백뿐인 값은 거부한다.

## 5. 오류 후 불변조건

모든 실패는 **원자적**입니다. 어떤 실패도 다음을 남기지 않습니다.

- 재고 수량의 부분 변경
- 출고 이력 레코드의 생성 또는 상태 변경
- `request_id` 사용 등록 (실패한 요청 번호는 정정 후 재사용 가능)

즉 "검증이 전부 끝나기 전에는 저장소를 변경하지 않는다"가 구현 규칙입니다(ADR-001 참조).

## 6. API 관찰 결과

전체 계약은 `docs/ARCHITECTURE.md`가 원천입니다. SPEC은 외부에서 관찰 가능한 결과만 고정합니다.

- 성공 응답은 HTTP `200`. 출고·취소 응답은 출고 레코드를 래핑 없이 반환하며 `status`, `movement_type`, `cancel_movement_type`, `stock_after`, `canceled_by`를 포함한다.
- 업무 규칙 위반은 HTTP `400` + `{"detail": "<한국어 실패 이유>"}`.
- 요청 형식 자체가 잘못되면(필드 누락·타입 오류) FastAPI 기본 동작으로 `422`가 나며, 이때 `detail`은 문자열이 아니라 객체 배열이다. Frontend는 두 형태를 모두 처리한다.
- 테스트가 고정한 실패 메시지 문구(변경 금지):

| 상황 | 메시지에 반드시 포함될 문구 |
|---|---|
| 필수값 공백 | `<필드 한글 라벨>` + `필수` (예: `출고 요청 번호`) |
| 수량 0·음수 | `출고 수량은 1 이상` |
| 재고 부족 | `재고가 부족` **및** `현재 재고: {가용}, 요청 수량: {요청}` (한 메시지에 함께) |
| 중복 요청 번호 | `이미 처리된 출고 요청 번호` |
| 재고 조합 없음 | `일치하는 재고` |
| 재취소 | `이미 취소된 출고` |
| 출고 건 없음 | 정확히 `출고 내역을 찾을 수 없습니다.` |

## 8. MVP 가정

아래는 요청사항과 테스트만으로 결정할 수 없어 이 SPEC이 **가정으로 고정**하는 사항입니다. 현업 확인 시 개정 대상입니다.

1. **WBS 유형 판정 규칙**: WBS 문자열을 공백 제거 후 **대소문자 무시 접두사**로 판정한다. `R2-00` 접두는 가수주, `R2-01` 접두는 하자보수, **그 외 전부 일반 프로젝트로 폴백**한다(미등록 유형을 오류로 막지 않는다).
2. **대소문자 정규화 범위**: 입력 정규화는 공백 제거만 수행하고 대소문자는 보존한다. 대소문자 무시는 이동유형 판정 내부에서만 적용한다. 따라서 재고 조회(WBS 필터 포함)는 대소문자 구분 정확 일치다.
3. **중복 판정 기준**: 공백 제거 후의 `request_id` 문자열 단독, 전역(재고 항목 무관) 기준. 성공한 출고만 등록되며, 실패한 요청의 번호는 재사용할 수 있다.
4. **재고 0 vs 재고 없음**: 재고 항목이 존재하지 않으면 "일치하는 재고 없음", 항목이 있으나 수량이 부족하면(수량 0 포함) "재고 부족"으로 구분한다.
5. **동시성**: 단일 프로세스·단일 워커 실행만 보장한다. 저장소에 락이 없으므로 멀티 워커 실행은 금지한다(RFC-001).
6. **취소자 검증**: 취소 요청의 `user_id`는 Pydantic 필수 문자열 검증만 적용하고 공백 검증은 추가하지 않는다.
7. **오류 식별**: 오류 응답에 기계 판독용 코드 필드를 두지 않는다. Frontend는 HTTP 상태로 성패를 판단하고 `detail` 문자열을 그대로 표시한다(문구로 분기하지 않는다).
8. **이력 정렬**: 출고 이력은 최신 건 우선으로 표시한다.
9. **타임스탬프**: `completed_at`·`canceled_at`은 로컬 타임존 ISO-8601 초 단위 문자열이다.
10. **이력의 자재 표기**: 출고 레코드에 `material_name`이 없으므로 이력 화면은 자재코드를 표기 기준으로 한다(자재명 표시는 Frontend가 재고 목록과 조인할 때만).

## 9. 변경 관리

- 이 SPEC은 승인 시점에 동결됩니다. 구현 중 얻은 변경·발견·회귀 이력은 SPEC에 추가하지 않고 `CHANGELOG.md`에만 기록합니다.
- 각 LOOP의 검증을 통과한 직후 CHANGELOG에 제품 변화를 기록하고 같은 단위로 commit합니다. 실패한 시도·예정 작업은 기록하지 않으며, 실습 마지막에는 누락과 버전 표기만 정리합니다.
- 가정(8장)이 뒤집히면: 사람 승인 → SPEC 개정 → 관련 테스트 조정 승인 → CHANGELOG에 개정 사실 기록 순서를 따릅니다.
